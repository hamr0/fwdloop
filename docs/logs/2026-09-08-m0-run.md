## Runner scope — read this before the table

`poc/m0/runner.mjs`'s `runDeclaration()` does **not** walk an arbitrary declaration JSON
step-by-step. It is a **hand-wired fold** matching the one job's fixed shape: `gather` (csv) →
`gather` (text) → `derive#1` (customer match) → `[ask if ambiguous]` → `derive#2`
(invoices/total/earliest-due/overdue-count) → `compose` → `ask` → `send`. The drafter
declarations (below, verbatim) prove a model **can** emit a valid step-kind sequence under the
schema and refuse an ungroundable step; the runner then proves **that shape** of flow, executed
step-by-step with fresh context per step, closes correctly and catches every planted error. It
does **not** prove a generic interpreter that would run an arbitrary declaration shape (Kimi's
draft merges derive#1+#2 into one `derive` step with 5 figures; GLM's keeps them separate — the
runner's fixed two-derive-step shape happens to be compatible with both, but a materially
different declaration would need the runner extended, not just re-pointed at a JSON file). This
is a scope limitation to carry into M2 (the real runner module), not a defect to silently paper
over — logged here per the brief, not fixed, since M0's job was the go/no-go on grounding, not
on a general interpreter.

## False-red count and fixes

3 false reds were found live and fixed (all in `poc/m0/close.mjs` or `poc/m0/runner.mjs`, none
by loosening what the close accepts as correct — verified by the regression tests added
alongside each fix, `poc/m0/close.test.mjs` / `poc/m0/runner.test.mjs`, 48/48 green):

1. **`closeCompose`'s bare-number regex didn't strip a bracketed ISO date** (`2026-06-09 [c3]`
   left `2026-06-` behind after the plain-number strip, since the date's hyphens broke the
   digit-run match) — tripped plant (d) on GLM-5.2's first clean attempt. Fixed by stripping the
   date-before-bracket pattern first. Regression test added.
2. **`runModelStep` self-poisoned its own retry**: a transport failure logged an unpriced
   (`costUsd: null`) spend row before checking whether to retry, so the retry's next
   `assertUnderGlobalCap()` call died on the row it had just written — surfacing the generic
   spend-guard message instead of `provider-red`. Fixed: a first-attempt transport-retryable
   failure retries silently with no row logged (nothing billed, nothing to account); only a
   terminal failure logs a row, and a pre-response failure logs `costUsd: 0` with a note
   (asserted, not defaulted) rather than `null`.
3. Two **prompt-completeness/formatting bugs**, not close bugs, left as prompt fixes per the
   standing rule ("never widen a close rule to turn a red green"): compose dropping citations a
   kept formula citation transitively needed (`c9`'s `daysBetween` input `c8` missing from the
   re-emitted array), and a bare ordinal list marker ("Invoice 1:", "Invoice 2:") tripping the
   bare-number check correctly (an uncited digit is uncited, regardless of what it labels).

None of these three were "the plant we were trying to catch" — all were runner/close
infrastructure bugs exposed by the FIRST real live traffic against them, caught because plant
(d) is specifically the run that must be clean, so any red on it is unambiguously a false red
per the brief.

## Findings (grammar gaps, truncations, provider errors, surprises)

- **GLM-5.2's plant (b) was never reached** — two consecutive genuine provider failures on
  `derive2` (`HTTP 524` then `read ETIMEDOUT`, the second after a 3045006ms/~51min hang before
  the runner had an explicit `timeoutMs` bound on the provider — fixed going forward to 300s per
  orchestrator ruling). `derive1` for plant-b was green both times, so this is not a grounding
  or close failure — it is a synthetic.new reliability issue on this specific model+step
  combination, observed on 3 separate attempts. Kimi-K3 caught plant (b) with the exact expected
  red string on the first try, so the close/plant mechanism itself is proven; GLM-5.2's cell N/N
  for (b) specifically is "not reached", not "failed".
- **`earliest_due` is expressed as a copied citation, not a derived `min`**: `close.mjs`'s
  `min`/`max` formula recomputes over `Number(citation.value)`; an ISO date string is not a
  number, so `min` over date citations cannot be independently recomputed. The closed grammar
  has no date-aware `min`. Per the brief's explicit instruction ("do not extend it: mark the
  figure as a FINDING"), this was **not** fixed — the model cites the correct due-date cell
  directly, which the close verifies is a real, correctly-quoted cell, but the close cannot
  independently prove that cell is the *earliest* one. A spec question for M1: either add a
  date-aware `min`/`max` to the closed formula grammar, or accept that "earliest" claims are
  copied-and-trusted rather than recomputed.
- **`count_overdue`'s close only recomputes `inputs.length` against the stated count** — the
  `count` formula has no filter primitive, so it verifies each individual `daysBetween` citation
  the model chose to include recomputes correctly, and that however many it included matches the
  stated count, but not that the model selected the *correct set* of overdue invoices. A model
  could in principle include the wrong invoices and still pass if the count coincidentally
  matches. Not fixed, per the same "closed grammar, don't extend it" instruction — logged as a
  spec question for M1.
- **The runner is a hand-wired fold for this one job's shape, not a generic declaration
  interpreter** (see "Runner scope" above) — a scope limitation for M2, not a defect.
- **F4 (retracted, already logged in FINDINGS.md) reconfirmed live**: GLM-5.2's reasoning can
  spend the entire output budget before answering; `maxTokens: 16000` on every round (per the
  brief) meant this never recurred in this session's model rounds (all `stopReason: end_turn`,
  none `max_tokens`) — the truncations seen during the drafter's earlier iteration were
  diagnostic and already priced/logged before this continuation started.
- **The spend ledger now carries one unpriced row** (`glm-5.2-plant-b` derive2, `read ETIMEDOUT`,
  `costUsd: null`) from the third plant-b attempt — a raw socket error not wrapped as an
  HTTP 5xx, so the runner's transport-retryable classifier didn't treat it as a known-$0
  pre-response failure. Per `spend.mjs`'s money-honesty rule, this permanently blocks
  `assertUnderGlobalCap` for any further LLM round in this session (unknown is never rendered as
  $0) — no further paid rounds are needed for M0, so this did not block anything else today, but
  **a human decision is needed** before any M0 continuation resumes real spend: either confirm
  $0 was actually billed for that request (synthetic.new dashboard) and correct the row the same
  way the two 524 rows were corrected, or accept the row as genuinely unpriced and raise the cap
  ledger's starting point accordingly.
